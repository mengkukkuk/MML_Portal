1 · What it uses — Frontend

Token custody in the browser

The SPA's security job is narrow but real: hold the access token somewhere XSS-resistant, attach it to every call, and never pretend the route guard is an access control.

Stack

React 19.1 + react-domSPA runtime
react-router-dom 7.6routing + guards
Zustand 5auth store
axios 1.16interceptors
MUI 7.1UI — escapes by default
Vite 8build + dev proxy
CLAUDE.md still describes Vue 3 + Pinia. On this branch that is stale — the running code is React + Zustand.

Where each token lives

  • Access token — a module-scope variable in api/client.js. Survives navigation, dies on reload. Never written to localStorage or sessionStorage.
  • Refresh token — HttpOnly cookie. JavaScript cannot read it at all, so an XSS payload cannot exfiltrate a long-lived credential.
  • The Zustand store keeps only a boolean hasToken plus the user profile — components can render conditionally without ever touching the token.

Route guard — RequireAuth.jsx

Reads three flags off the matched routes' handle:

  • requiresAuth → redirect to /login?redirect=…
  • requiresRole → redirect to / on role mismatch
  • isLoginRoute → bounce signed-in users off /login
This is navigation UX, not authorization. Anyone can call the API directly. The only real gate is the FastAPI dependency on each endpoint — see the RBAC step.

Safe expression evaluator — mathExpr.js

Live panels let an admin write a value transform such as value/10. That string is admin-supplied data rendered in every viewer's browser, so it must not be executable.

  • Hand-written tokenizer + recursive-descent parser
  • No eval, no new Function, no DOM or prototype access
  • Fixed function table — abs sqrt pow min max floor ceil round
  • Only identifier recognised is value
A transform string can produce a wrong number. It cannot produce code execution.
1 · What it uses — Backend

Primitives and where they are enforced

No third-party auth framework, no ORM. Password hashing is stdlib, tokens are PyJWT, and authorization is expressed as FastAPI dependencies that every protected route declares explicitly.

Password hashing — security.py

# stored format, self-describing
scrypt$<salt_hex>$<digest_hex>

N     = 16384   # CPU/memory cost
r     = 8
p     = 1
dklen = 64      # 64-byte derived key
salt  = os.urandom(16)  # per user
  • hashlib.scrypt — memory-hard, stdlib only, no native wheel needed on Python 3.14
  • Fresh 16-byte random salt per password; stored inline, so parameters can be migrated later
  • Comparison uses hmac.compare_digest — constant time
  • A malformed stored hash returns False, never raises

Tokens — PyJWT, HS256

TypeLifeCarried in
access30 minJSON body → Authorization: Bearer
refresh7 daysHttpOnly cookie, path=/api/auth
reset30 minemailed link, single use

Every token is stamped with iat, exp, a random jti, and an explicit type claim. Each verifier re-checks the type, so a refresh token cannot be replayed as an access token.

The access token carries role, but get_current_user ignores it and re-reads the user row from the database — a deleted or demoted account loses access without waiting for token expiry.

Enforcement points — auth.py

def get_current_user(creds = Depends(bearer_scheme)):
    payload = security.decode_token(creds.credentials)   # signature + exp
    if payload.get("type") != "access": raise InvalidTokenError
    user = db.get_user_by_id(int(payload["sub"]))    # DB is the truth
    if user is None: raise HTTPException(401)
    return user

def require_admin(current_user = Depends(get_current_user)):
    if current_user["role"] != "admin": raise HTTPException(403)
    return current_user
  • Any decode failure — bad signature, expired, wrong type, missing sub — collapses to one generic 401 "Invalid or expired token". No oracle for the attacker.
  • Three levels exist: get_current_user, require_operator_or_admin, require_admin.
  • Other libraries in the chain: Pydantic (request-body typing and length bounds), psycopg 3 (parameterized SQL, sql.Identifier), python-dotenv (config load).
1 · What it uses — Secrets

Every secret in the system, and how it is held

Five distinct secrets. Three are held correctly, one is held in plaintext by design, and one has a fallback default that will silently boot an insecure deployment.

SecretLives inAt restExposure
User passwords users.password_hash scrypt, salted Never returned by any endpoint. users is in SENSITIVE_TABLES, so it cannot be charted.
JWT_SECRET .env plaintext file Signs all three token types. Compromise = full account impersonation.
APP_DB_PASSWORD config.py source hardcoded literal The app/config database is fixed at localhost and its password is a literal in committed source, not .env. Tolerable only because the credential is worthless off-box: it must be paired with a loopback connection. It stops being tolerable the moment pg_hba.conf accepts that user from a non-loopback address — see the gaps table.
Datasource passwords datasources.password plaintext column All plant credentials now live here rather than in .env — one row per plant database. Never returned: the public projection exposes only (password <> '') AS has_password. The blast radius of a read of the app database therefore grew from one database to every plant.
BREVO_API_KEY / SMTP_PASS .env plaintext file Sent as a request header; error logging deliberately truncates response bodies rather than echoing key material.

Two layers keep datasource passwords out of reach

  • Projection — _DS_PUBLIC_COLS never selects password; the API returns a boolean instead. On update, a null password keeps the stored secret rather than blanking it.
  • Denylist — SENSITIVE_TABLES = {users, dashboard_panels, mmldatabuffer, datasources}. Without this, an admin could bind a panel's filter column to datasources.password and read secrets out through the distinct-values picker.
The denylist is the load-bearing control here, and its purpose is documented at the definition site. Adding a new credential-bearing table means adding it to that set.

Config defaults that do not fail closed

# config.py — the _get() helper raises on missing vars…
def _get(name, default=None):
    if value is None: raise RuntimeError(...)

# …but the one secret that matters most does not call it:
JWT_SECRET  = os.getenv("JWT_SECRET", "dev-insecure-change-me")

# and the app database is not configurable at all:
APP_DB_HOST     = "localhost"
APP_DB_PASSWORD = "P@ssw0rd"
CLAUDE.md and .env.example call JWT_SECRET required. The code treats it as optional with a default. A deployment that forgets it starts successfully and signs every token with a value published in this repository — anyone can then mint a valid admin token. Carried to the gaps step as item #1.

The hardcoded APP_DB_PASSWORD is a deliberate trade: it removes a whole class of "the app will not boot because .env is wrong" failures, and the credential only works over loopback. That guarantee is enforced by pg_hba.conf, not by this code — nothing here fails closed if the operator widens it.
Seeded accounts. seed_users.py upserts two demo accounts — one admin, one operator — with known passwords committed to the repo, and re-applies them every time it runs. It is a local-auth testing helper. If it has been run against a production database, both passwords must be rotated and the script kept out of the deployment path.
1 · What it uses — Deployment

Transport, origin, and cookie posture

The production shape is IIS in front of a loopback-bound FastAPI service. TLS exists only on the outer hop, which is what makes the cookie's Secure flag a deployment decision rather than a constant.

The inner hop is plaintext by design — it never leaves the host. That assumption breaks the moment the service binds 0.0.0.0.

Cookie attributes — auth.py

httponlyTrueblocks JS read
samesitestrictblocks cross-site CSRF
path/api/authnot sent to data endpoints
max_age7 daysmatches token exp
secureenv-controlleddefaults to false
COOKIE_SECURE must be set to true on any HTTPS deployment. Left at its default, the refresh cookie will be transmitted over a plain-HTTP request to the same host.

CORS — main.py

_ORIGINS = os.getenv("CORS_ORIGINS",
    "http://localhost:5173,http://127.0.0.1:5173").split(",")

app.add_middleware(CORSMiddleware,
    allow_origins=_ORIGINS,      # explicit list
    allow_credentials=True,     # forbids "*"
    allow_methods=["*"], allow_headers=["*"])
  • allow_credentials=True makes a wildcard origin structurally impossible — the browser rejects it. The allowlist is therefore enforced, not merely intended.
  • In the standard IIS deployment the SPA and API share an origin, so CORS is not on the request path at all; it matters for the Vite dev server and any split-host setup.
  • Set CORS_ORIGINS in production. Left unset, the two localhost dev origins stay allowlisted.
2 · How it works — Login

From password to two tokens

One round trip. The response body carries the short-lived credential; the long-lived one is written straight to a cookie the page's own JavaScript can never read.

Login. The refresh token never appears in the response body — the handler comments call that out explicitly.

What this gets right

  • Unknown username and wrong password produce an identical 401 body — no user enumeration.
  • Failed attempts are logged with the attempted username, giving detection a signal.
  • Self-registration hardcodes SELF_REGISTER_ROLE = "operator". The role is never read from the request body, so privilege escalation via a crafted registration payload is not possible.
  • Password length is validated against MIN_PASSWORD_LEN on register, change, and reset alike.

What it does not do

  • No rate limiting and no lockout. Nothing in the app or in web.config throttles /api/auth/login. Password guessing is bounded only by scrypt's cost per attempt.
  • Timing is not equalised: a missing user short-circuits before the scrypt derivation runs, so a non-existent username answers measurably faster than a real one.
  • Registration is open to anyone who can reach the API. If that is not intended, it needs to be disabled at the router.
2 · How it works — Session continuity

The 401 interceptor

A 30-minute access token means an open dashboard will hit 401 mid-session. The axios response interceptor absorbs that: one refresh, a queue for everything in flight, and a hard redirect if the refresh itself fails.

Session continuity. The _retry flag and the /auth/ exclusion together guarantee a failed refresh terminates instead of looping.

Design properties

  • The refresh cookie is scoped to path=/api/auth, so it is not attached to the dozens of polling calls the Live grid makes. Less exposure, smaller requests.
  • A refresh re-reads the user from the database, so revoking an account takes effect at the next refresh rather than at token expiry.
  • Transient failures (502/503/504 and network timeouts) get exactly one retry — deliberately separated from the auth path so a gateway blip is not mistaken for a session end.

Rotation is partial

# auth.py — rotate refresh token (…) old one stays
# valid until expiry in this simple in-memory
# implementation, but production should add to denylist
new_refresh = security.create_refresh_token(user_id)
_set_refresh_cookie(response, new_refresh)
A new refresh token is issued on every refresh, but the previous one is not denylisted. A stolen refresh token therefore stays usable for its full 7-day window even after the legitimate user's cookie has rotated past it — so rotation here does not give you stolen-token detection. The code comments this honestly.
2 · How it works — Logout

Revocation, and the shape of its limits

Logout does two things: denylists the refresh token's jti and deletes the cookie. Both the strength and the weakness come from where that denylist lives.

The sequence

  • 1. SPA calls POST /api/auth/logout; the browser attaches the refresh cookie automatically.
  • 2. Server decodes it, extracts jti, adds it to _revoked_refresh. An already-invalid token is silently ignored — nothing to revoke.
  • 3. delete_cookie with matching path and attributes, then 204 No Content.
  • 4. Client-side _clearSession() drops the in-memory access token and resets the store. This runs in a finally block, so a failed network call still logs the user out locally.

Where revocation state lives

# auth.py — module-level, process-local
_revoked_refresh: set[str] = set()
_used_reset:      set[str] = set()

Two consequences follow directly, and the source comments state both:

  • A service restart clears the denylist. A refresh token revoked by logout becomes valid again after the next deploy, NSSM restart, or crash — for whatever remains of its 7 days.
  • Single-worker only. With more than one uvicorn worker, a logout handled by worker A does not revoke anything in worker B, and a reset link consumed in one worker can be replayed in another.
The fix is the same for both: move jti denylisting into Postgres (or Redis) with a TTL matching token lifetime. Until then, revocation is best-effort within one process lifetime.
The access token is never revocable by design — it is stateless and short-lived. Its 30-minute lifetime is the containment window. Shortening ACCESS_EXPIRE_MIN tightens that window at the cost of more refresh traffic.
2 · How it works — Password reset

Out-of-band, generic, single use

The reset flow proves control of a mailbox rather than knowledge of a password. Its two interesting properties are that the request endpoint reveals nothing, and the token can only be spent once.

Password reset. Delivery runs as a FastAPI BackgroundTask so a slow relay cannot stall the response — or leak timing information about whether the address existed.

Properties worth keeping

  • Generic response. Registered and unregistered addresses get byte-identical replies, and because the send is backgrounded they also get near-identical timing.
  • Single use. The jti is recorded after a successful password change, so the same link cannot be replayed.
  • Short life. 30 minutes by default, and the expiry is stated in the email body.
  • Silent failures. send_password_reset never raises; SMTP and Brevo errors are logged, never surfaced. Brevo error bodies are truncated so key material cannot ride along into the log.

Two operational hazards

  • Log-only mode is a live credential channel. With neither BREVO_API_KEY nor SMTP_HOST set, mailer.py writes the full reset URL to the service log at INFO. That is intended as a dev convenience — in production it hands account takeover to anyone who can read logs/.
  • The token rides in a query string. {APP_BASE_URL}/reset-password?token=… lands in browser history, and would land in any proxy or access log that records query strings. Bounded by the 30-minute expiry and single use, but worth knowing.
  • No rate limit on forgot-password — it can be used to send repeated mail to a known address.
2 · How it works — Authorization

The role map, endpoint by endpoint

Two roles exist: admin and operator. The rule of thumb is "reads for any authenticated user, writes for admin" — with two deliberate exceptions and one asymmetry worth reviewing.

Endpoint groupReadWriteNotes
/api/auth/* public public login, register, refresh, logout, forgot/reset-password. me and change-password require a valid token.
/api/users/* admin admin Full CRUD is admin-only — including list. The only endpoint group where reads are gated too.
/api/readings/* any user — Read-only telemetry.
/api/tags/* any user — Read-only telemetry.
/api/panels/* any user admin Exception: PATCH /{id}/poll-interval uses require_operator_or_admin — an operator may retune polling without gaining panel-editing rights.
/api/dashboards/* any user admin Create / update / delete are admin-only.
/api/datasources/* any user admin Reads are password-free. POST /test is admin-only because it opens an outbound connection to an arbitrary host.
/api/schema/* any user — Table / column / distinct-value catalogue. Accepts datasource_id. See the note below.
/api/alarms/*, /api/events/* any user any user Acknowledge is available to any authenticated user, with the acting user recorded.
/health public — Liveness probe for NSSM. Returns {"status":"ok"} only — no version or config disclosure.

Why the model holds

  • Authorization is a declared dependency on every route, not middleware pattern-matching on URLs. A new endpoint without a dependency is visibly unprotected in review rather than silently covered by a wildcard.
  • The role is read from the database row, not from the token claim, so it cannot be forged by re-signing and cannot go stale.
  • Self-registration cannot produce an admin — SELF_REGISTER_ROLE is a module constant, not a request field. Roles are only assignable through the admin-gated /api/users endpoints.
  • But registration itself is ungated. POST /api/auth/register takes no token, no invite, no flag — so the whole "any user" column above is one anonymous request away. Gaps item #5.

The asymmetry to review

datasources.py gates its connection test on require_admin, and says why: "The test endpoint can probe arbitrary hosts, so it is admin-only."

All five /api/schema/* endpoints also accept a datasource_id — and all five are gated on get_current_user, not require_admin.

Net effect: any authenticated operator can enumerate tables, columns, and distinct column values on every admin-configured remote database, using the admin's stored credentials. The SENSITIVE_TABLES denylist limits what is reachable on the app's own database, but a remote datasource's tables are only filtered by that same fixed name list. Either intentional (operators build panels) or an oversight — worth an explicit decision.
2 · How it works — Injection defence

Dynamic table and column names, safely

The Live grid lets an admin chart any numeric column of any non-sensitive table. That means table and column names arrive from HTTP — and identifiers cannot be parameterized. This is the most interesting security mechanism in the codebase.

The validation gate lives in db.py's _table_columns() / _safe_identifiers() — every dynamic-SQL builder must pass through it first.

What makes this sound

  • All SQL lives in one module. db.py is the only file that writes queries — routers pass values, never fragments. One place to audit.
  • Allowlist, not sanitisation. A name is accepted only if PostgreSQL itself reports it as an existing base table/column. There is no escaping heuristic to bypass.
  • Then still quoted. Even a validated name goes through sql.Identifier rather than string concatenation — defence in depth against a name containing quotes or case surprises.
  • Bounded input. Pydantic Query constraints cap limit at 2000 and the series window at 10080 minutes, so a single call cannot ask for unbounded work.

The f-strings that are not injection

# db.py — looks alarming, is not
select_metrics = ", ".join(
    f'{_FIELD_DB_COLUMN.get(f, f)} AS {f}'
    for f in fields)          # ← from _discover_tag_fields()

sql = f"SELECT tag_name, active, … {select_metrics} "
      "FROM public.variables_tag WHERE tag_name = %s"
These interpolate column names discovered from information_schema at startup — server-controlled data, not request data. The tag name itself is still a %s parameter. Same pattern for _PANEL_COLS, _DASH_COLS, _DS_PUBLIC_COLS: fixed constants defined in the module. Worth a comment at each site so a future reader does not have to re-derive it.
Closing

Known limitations and the hardening order

Everything here is visible in the source, and several items are already acknowledged in code comments. Ordered by what a real deployment should fix first.

Deployment-blocking

ItemWhereFix
1 · JWT_SECRET has a public default
Docs say required; code says optional		 config.py Route it through the existing _get() helper so a missing value refuses to boot.
1b · App DB password is a source literal
Safe only while Postgres refuses it off-loopback		 config.py · pg_hba.conf Confirm pg_hba.conf grants the postgres user host access from 127.0.0.1/32 and ::1/128 only. Widening it to a subnet turns a published literal into a remote credential. Verify after any PostgreSQL upgrade — installers rewrite this file.
1c · Plant credentials concentrate in one table
Read access to the app DB now yields every plant		 datasources.password Stored plaintext. Encrypt at rest with a key held outside the database, so a stolen backup is not a set of live plant logins. Until then, treat app-DB backups at the same classification as the plant credentials themselves.
2 · COOKIE_SECURE defaults to false auth.py Set COOKIE_SECURE=true in every HTTPS .env; consider inverting the default.
3 · Seeded demo accounts
Known passwords, re-applied on every run		 seed_users.py Rotate both if it has ever run against production; keep the script out of the deploy path.
4 · Reset links written to the log
Only when no mailer is configured		 mailer.py Always configure BREVO_API_KEY or SMTP_HOST in production; restrict access to logs/.
5 · Self-registration is open to anyone
No invite, no approval, no feature flag		 auth.py — POST /api/auth/register Gate it behind require_admin, an invite token, or an ALLOW_SELF_REGISTER flag defaulting to off. The SPA has no /register route, so nothing in the UI depends on it today.
Why this one ranks above the architectural items. The endpoint is unauthenticated and mints a working operator account. Everything in the "any user" column of the role map — all telemetry, every dashboard and panel, alarm acknowledgement — is reachable from that account, and so is item 11: catalogue enumeration against every admin-configured remote database, using the admin's stored credentials. On a plant network that turns "can reach the API" into "can read the plant". Because the SPA never links to it, the exposure is easy to miss during review.

Architectural — acknowledged in code

ItemWhereImpact
6 · Revocation state is in-memory auth.py — _revoked_refresh, _used_reset Logout revocation and single-use reset both reset on restart, and neither works across multiple workers.
7 · Refresh rotation without denylisting auth.py — comment at the rotation site A stolen refresh token remains valid for its full 7 days; no reuse detection.
8 · Open redirect on the login bounce RequireAuth.jsx — flagged in its own docblock /login?redirect=//evil.com is honoured. Pre-existing, carried over from the Vue router.
9 · No rate limiting anywhere login, register, forgot-password Password guessing and mail-flooding are bounded only by scrypt cost and network speed.
10 · Datasource passwords stored plaintext db.py — password TEXT Deliberate parity with the app's own .env credential. Mitigated by the public projection and the table denylist; DB-file read access still yields them.
11 · /api/schema/* open to operators schema.py vs datasources.py Operators can enumerate remote datasource catalogues. Inconsistent with the admin gate on the connection test.

Controls that are working as intended

  • scrypt with per-user salt and constant-time comparison
  • Access token never persisted; refresh token unreadable by JavaScript
  • Refresh cookie scoped to /api/auth with SameSite=Strict
  • Explicit CORS allowlist, enforced by allow_credentials=True
  • Token type claims checked at every verifier
  • Role re-read from the database on every request
  • Self-registration cannot escalate to admin — though it is ungated, see item 5
  • Generic responses on login and forgot-password
  • SQL identifiers allowlisted then quoted; values always parameterized
  • SENSITIVE_TABLES keeps credential tables off the charting surface
  • mathExpr.js parses instead of evaluating — no eval, no Function
  • All SQL confined to db.py

Scope of this document

This is a design document describing the security architecture as implemented on branch react_cvt, read from source. It is not a penetration test and not an exhaustive audit — nothing here was verified by running exploits against a deployment.

The limitations listed above are the ones legible from reading the code. Absence from this list is not evidence of absence.
